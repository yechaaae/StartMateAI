# Branch & Commit (StartMateAI)

작업 트리에 쌓인 변경을 깔끔한 새 브랜치 + 논리 단위 커밋으로 정리하는 절차다.
핵심 가치는 **사용자가 브랜치 이름을 직접 고르고**, 커밋이 **관심사별로 한눈에 읽히게**
나뉘는 것. 한 PR을 리뷰하는 사람이 커밋 목록만 봐도 "무슨 일을 했는지" 파악되게 만든다.

## 0. 시작 전 확인

- `git status --short` 와 `git diff --stat` 으로 무엇이 바뀌었는지 먼저 파악한다.
- 변경이 이미 인덱스에 staged 되어 있을 수 있다(예: stash pop 직후). 그러면 `git reset -q`
  로 일단 전부 unstage 한 뒤 커밋 단위로 다시 선택 스테이징하는 편이 통제하기 쉽다.
- 지금 어느 브랜치인지 확인한다. 보통 `main` 위 미커밋 변경에서 시작한다.

## 1. 브랜치 이름을 먼저 "추천"한다 (사용자가 결정)

절대 바로 만들지 말 것. 이 스킬의 약속은 **추천 → 사용자 판단 → 생성** 순서다.

1. `git log --oneline -15` 등으로 최근 브랜치/머지 컨벤션을 본다. StartMateAI는
   `feat/...`, `feature/...`, `fix/...`, `docs/...` 접두사를 쓴다(예: `feat/https-nginx`,
   `feature/operation-feedback`).
2. 변경 내용을 한 줄로 요약해 그 컨벤션에 맞는 이름 후보 2~4개를 만든다.
3. `AskUserQuestion` 으로 제시한다. **첫 번째를 추천안**으로 두고 라벨 설명에 근거를 적는다.
   브랜치를 만들면 미커밋 변경이 그대로 새 브랜치로 따라오고 `main`은 origin과 동일하게
   유지된다는 점을 한 줄로 안내한다.
4. 사용자가 고르거나 직접 입력할 때까지 기다린다.

## 2. 브랜치 생성

사용자가 이름을 확정하면:

```bash
git switch -c <선택된-브랜치-이름>
```

`switch -c`는 작업 트리 변경을 그대로 가져온다. `main`은 건드리지 않는다.

## 3. 분할 계획 세우기

변경을 **관심사(기능/영역) 단위**로 묶는다. 보통 이런 축으로 나뉜다:

- 영역: 백엔드(BE) / 프론트(FE) / AI / 문서(DOCS)
- 기능: "운영 피드백 폼"과 "textarea 리사이즈"처럼 서로 다른 작업은 별도 커밋
- 종류: 기능 추가(feat) / 버그 수정(fix) / 스타일(style) / 설정(chore) / 문서(docs)

원칙: **한 커밋 = 하나의 일관된 변경**. 무관한 변경(예: 우연히 같이 있던 설정 파일)은
따로 떼어 자체 커밋으로 만든다. 사용자가 "전부 분할 커밋"을 원하면 빠뜨리지 말고 모두 담되,
서로 다른 의도는 섞지 않는다.

계획이 복잡하면 커밋 목록(순서 + 메시지 제목 + 포함 파일)을 사용자에게 먼저 보여줘도 좋다.

## 4. 한 파일이 여러 관심사를 담을 때: hunk 단위 분리

가장 흔한 함정. 예를 들어 `App.css`에 "기능 스타일"과 "전역 textarea 수정"이 같이 있으면
파일 통째로 한 커밋에 넣으면 분류가 어긋난다. **hunk 단위로 쪼개 스테이징**한다.

1. `git diff <파일> | grep -nE "^@@"` 로 hunk 경계를 파악한다.
2. `git add -p <파일>` 로 원하는 hunk만 고른다. 비대화로 답을 파이프할 수 있다
   (각 hunk에 y/n). 예: 5개 hunk 중 4번째만 담기 →

   ```bash
   printf 'n\nn\nn\ny\nn\n' | git add -p <파일> >/dev/null 2>&1
   ```

3. **커밋 전 반드시 검증**한다:

   ```bash
   git diff --cached <파일> | grep -nE "^@@|<핵심키워드>"
   ```

   의도한 hunk만 staged 됐는지 눈으로 확인한다. 어긋나면 `git reset <파일>` 후 다시.
4. 나머지 hunk는 다음 커밋에서 `git add <파일>` 로 한 번에 담으면 된다.

## 5. 커밋 — StartMateAI 메시지 형식

각 커밋은 아래 형식을 따른다. 제목은 **한글**, 영역 태그는 대괄호로.

```
[FE|BE|AI|DOCS 중 하나] <type>: <한글 제목>

- <상세 변경 1>
- <상세 변경 2>
```

- 영역 태그: `[BE]` `[FE]` `[AI]` (문서 전용이면 `[DOCS]`도 가능하나, 사용자가
  AI/FE/BE 중 하나만 쓰라고 하면 문서도 관련 영역 태그 + `docs:` 로 처리한다).
- type: `feat` `fix` `style` `chore` `docs` 등 conventional 류.
- 본문은 빈 줄 뒤 한글 불릿으로 핵심 변경을 적는다.

**중요 규칙**

- ❌ `Co-Authored-By` 트레일러를 **넣지 않는다**(사용자 선호).
- 멀티라인/한글 메시지는 heredoc + `git commit -F -` 가 가장 안전하다:

  ```bash
  git commit -F - <<'EOF'
  [FE] feat: 운영 피드백을 사용자 직접 입력 폼으로 개편

  - 매출/지출/주문수/전환율 직접 입력, 직전 저장값 대비 증감% 자동 표시
  - 상품 추가/삭제·비중 잠금·이력 패널 추가
  EOF
  ```

## 6. 마무리

- 각 커밋 후 `git log --oneline` 으로 결과를 확인하고, 마지막에 `git status`가 clean 한지 본다.
- **푸시는 사용자가 명시적으로 요청할 때만** 한다. 끝나면 커밋 목록을 표로 요약하고
  "원격에 push 할까요?"라고 물어본다.
- `main`이 origin과 동일하게 유지됐는지 확인한다.

## 예시 흐름 (이 워크플로가 만들어진 실제 사례)

1. 변경 13개 파일 파악 → 브랜치 후보 3개 추천 → 사용자가 `feat/operation-feedback-manual-input` 선택
2. `git switch -c feat/operation-feedback-manual-input`
3. 5개 커밋으로 분할: `[BE] feat`(백엔드) / `[FE] feat`(폼 개편) / `[FE] style`(textarea) /
   `[BE] chore`(설정) / `[FE] docs`(문서). `App.css`는 hunk 분리로 기능 스타일은 폼 커밋,
   resize 변경은 textarea 커밋에 각각 배치.
4. 트리 clean 확인 → push 여부 질의(미요청이면 보류).
